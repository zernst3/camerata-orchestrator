## Why cache writes far exceed reads

Measured (sweep5b and reruns, `*-inspect.log` line `Token usage`):

| run | input | cache write | cache read | write share of input | calls | read per call |
|---|---|---|---|---|---|---|
| faktura sweep5b | 742K | 661K | 81K | 89% | 79 | 1.0K |
| hearth sweep5b | 1,421K | 1,340K | 80K | 94% | 90 | 0.9K |
| hearth sweep5 | 1,015K | 904K | 110K | 89% | 93 | 1.2K |
| hearth w19 | 1,806K | 1,722K | 83K | 95% | 102 | 0.8K |
| hearth smoke (7 calls) | 253K | 188K | 64K | 75% | 7 | 9.2K |
| lumen | 992K | 920K | 72K | 93% | 119 | 0.6K |
| tutorly | 781K | 702K | 79K | 90% | 88 | 0.9K |
| supabase-portal | 704K | 624K | 80K | 89% | 70 | 1.1K |

Four facts explain it.

1. **These runs did not exercise Camerata's cache placement at all.** Every sweep log ends with `backend: cli`. On the CLI backend (`crates/llm/src/llm.rs:164-170`, `claude -p --output-format stream-json`) `LlmRequest::cache_breakpoints` is never serialized; the doc on `audit_pass` (`ai_audit.rs:3704-3709`) says so. The cache columns in the logs are the Claude Code harness's own `cache_control` usage reported back through stream-json (`llm.rs:549-556`), priced by the CLI's `total_cost_usd`. Each `claude -p` call is a fresh one-shot process whose whole prompt (harness system prompt plus Camerata's repo map, digest and rules) is written to cache by the harness and never read back by anyone, because no later call shares that exact prefix in a fresh session. That is why 89 to 95 percent of all input tokens are writes.

2. **The reads are a fixed quantity, not Camerata's repo map or digest coming back.** Cache read totals sit at 64K to 110K for runs of 7 to 119 calls on repos of very different sizes. A re-read of Camerata's own prefix would scale with repo size and call count; a constant total means the reads are harness-level (the Claude Code system prompt and tool definitions shared across calls launched close together). Camerata's repo map and digest were re-read approximately zero times in every sweep.

3. **On the API path the design would still be write-heavy, because of scheduling.** `run_passes` orders work chunk-major (`ai_audit.rs:3933-3935`) and runs `buffer_unordered(6)` (`:4018`) with `RULE_BATCH_SIZE = 15` (`:3819`). For a chunk with 10 rule-batches, the first 6 requests are in flight simultaneously. An Anthropic cache entry becomes readable only after the first response starts, so all 6 miss and each writes the repo map plus digest (about 11K tokens on hearth) at 1.25x. Only rule-batches 7 to 10 read. Expected: about 60 percent writes, 40 percent reads of the digest segment. The repo-map segment (breakpoint 1) does get read across chunks once the first chunk's response has started, which is the only read the design reliably earns.

4. **Byte identity is fine within a scan; it breaks across modes and groups.** `build_pass_prompt` (`:3680-3698`) is shared by parallel and batch mode and the prefix `Repository: {repo}\n\n{repo_map}` carries no chunk index, so it is byte-identical across chunks. The chunk segment `({label} {ci+1}/{n_c})\n\n{digest}` is identical across a chunk's rule-batches. Two things do vary: `label` differs per routing group (so the second group's chunks never hit the first group's entries even though the digest bytes are the same), and the system prompt is sent as a plain `system` string that is part of the hashed prefix but carries no breakpoint of its own (harmless on the API, since the first user-content breakpoint covers it). The rules block, which is the longest content shared ACROSS chunks (the same 15 rules are sent to every chunk), sits last and is never cached. In batch mode (`n_b = 1`) the digest breakpoint is dropped (`:3654-3664`), correctly, but items in a Message Batch complete over minutes to hours and the default 5m TTL (`llm.rs:947-963`, 1h is opt-in) means even the repo-map entry will usually have expired between items.

Consequences for the plan: (a) any API-cost projection made from the sweep logs' cache columns is a projection of the Claude Code harness, not of Camerata; one API-backend fixture run is needed before cache work is tuned; (b) fix scheduling so a chunk's rule-batches are not concurrent with each other (warm one pass, then fan out), or reorder the prompt so the rules block leads and the per-chunk digest trails, which makes "same rule-batch across many chunks" the shared prefix and lets chunks run concurrently without the race; (c) set 1h TTL automatically in batch mode; (d) record cache read and write per stage so the ratio is visible per run.

## Why routing yields only a 3 percent input reduction

`scan_routing.rs` knows exactly two scopes (`:28-33`): `Language(x)` and `All`. Scope is inferred from the rule id's first token against `LANGUAGE_PREFIXES` (`:63-99`), nothing else. The corpus prefixes (counted over `crates/rules/principles`) are RUST 60, JAVASCRIPT 51, ARCH 48, SUPABASE 35, GO 33, PYTHON 32, CSHARP 31, JAVA 25, RUBY 20, ORCH 18, SEC 14, SQL 11, CICD 11, PROC 10, UI 7, TESTING 7 and a few others. On a Next.js plus Supabase repo like hearth the selected 147 rules split roughly 45 JAVASCRIPT (routed to `web`) and about 100 others (ARCH, SUPABASE, SEC, SQL, CICD, UI, TESTING, PROC) that all land in `All` and are sent to every file. The log confirms it: always `2 groups`.

`saved_fraction` (`:160-166`) is `1 - routed_chars / (total_chars x rules)`. With about 30 percent of rules routed and web files making up roughly 90 percent of hearth's bytes, the saving is 0.3 x 0.1 = 3 percent. The 10 percent on sweep5b hearth vs 3 percent on sweep5, smoke and w19 for the same zip reflects a different `files` set between runs, not a routing change. Three things would make routing matter:

1. **Domain and path scope, not language prefix.** The corpus already carries `domain` on 424 rule files (`sql`, `supabase:auth`, `ci-cd`, `api-layer`, `rust:seaorm`, ...). SUPABASE and SQL rules belong on `.sql`, `supabase/**` and `config.toml`; CICD rules on `.github/**` and pipeline files; TESTING on test paths; UI on component paths. Routing on `domain` plus a per-rule `applies_to` glob (new field, corpus change) moves most of the `All` group into narrow groups.
2. **Per-file-type grouping of the `All` remainder.** Even cross-cutting ARCH and SEC rules rarely apply to `.md`, `.json`, `.toml` or `.sql`; a file-type exclusion list per rule family is a cheap, auditable narrowing.
3. **Batch mode applies no routing** (`ai_audit.rs:7095-7101`), so the mode the plan wants as default currently sends every rule to every file.

Recall caveat: every narrowing is a potential silent miss. `All` must remain the fallback for any rule without declared scope, the advisory pass must keep whole-repo view, and each routed rule must be checked against the fixture defects it is supposed to catch before its scope is tightened.
